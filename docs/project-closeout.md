# Closing out a project

What to do when a study ends. Takes about an hour and ensures reproducibility.

---

## Why this matters more than it sounds like it does

At foundry10, when a study closes, **data is archived on Forge and deleted from Google Drive and from local machines.** That is good data hygiene.

It also means that from that moment on, the only connection between the code in this repository and the data it was run on is whatever someone wrote down.

If nobody records the Forge location, the repository becomes a set of scripts that read `data/raw/survey.csv` — a file that no longer exists anywhere anyone can find. Nobody notices for two years, and then a reviewer asks for a robustness check, or a new postdoc wants to extend the work, and the answer is that it cannot be done.

---

## 1. Finish the repository

- [ ] Every analysis reported in the final report is in `code/`
- [ ] `code/run_all.R` runs start to finish without error — **actually run it**, from a fresh R session, before the data disappears. This is your last chance to find out that a step was only ever run interactively.
- [ ] Every figure and table in the final report is regenerated by the code, and the numbers match the final report
- [ ] `docs/session-info.txt` reflects the final run
- [ ] Reports in `reports/` are re-rendered against the final analysis, so they do not show superseded numbers
- [ ] `docs/decisions.md` is complete, including anything decided during peer review
- [ ] `docs/codebook.md` documents the final analytic variables
- [ ] Exploratory scripts that went nowhere are deleted or clearly labeled — a folder of eleven half-finished scripts helps nobody

---

## 2. Archive the data

- [ ] Data archived on Forge according to the standard process
- [ ] **`data/README.md` updated with the Forge location or identifier, the archive date, and who archived it**
- [ ] The Google Drive link in `data/README.md` is marked as no longer active
- [ ] `data/README.md` records how a future researcher requests access to the archived data, and from whom
- [ ] Data removed from Google Drive
- [ ] Data removed from every local machine — ask each team member to confirm, including anyone who has left the project

The second item is the one that matters. Everything else on this page is housekeeping; that line is the whole point.

---

## 3. Update the README

- [ ] Status changed to `published` or `complete`
- [ ] Citation added, with DOI
- [ ] Link to the published paper
- [ ] Contact updated to someone who will still be here — if the project lead is leaving, this must be a role or an ongoing staff member.

---

## 4. Decide on visibility

- [ ] Decision made about whether this becomes public
- [ ] If public: [`before-going-public.md`](before-going-public.md) completed and approved
- [ ] If it stays private: note why in the README, so the next person does not have to reconstruct the reasoning

---

## 5. Hand off ownership

Repositories outlive the people who create them. Before the project lead moves
on:

- [ ] Repository is owned by the **`foundry10-research` GitHub organization**, not a personal account
- [ ] The research admin (currently Amy Ly) has admin access
- [ ] The director of the research pillar (currently Dominic Gibson) has admin access
- [ ] Departing team members have been removed as collaborators
- [ ] Anything the repository depends on that is tied to one person — an OSF project, a Qualtrics account, a Drive folder — has been transferred or documented

---

## 6. Archive the repository

Once everything above is done, GitHub's archive feature marks the repository read-only and displays a banner saying it is no longer actively maintained.

Settings → Danger Zone → **Archive this repository**

This is reversible, and it is a clear signal to future readers that what they are looking at is final rather than abandoned.

- [ ] Archived

---

## The one-sentence version

If you do nothing else on this page: **write the Forge location into `data/README.md` before the data leaves Google Drive.**
